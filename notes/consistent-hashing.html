Consistent hashing

The problem it solves: with plain hash(key) % N sharding, adding or removing a single node changes N, which remaps almost every key to a different node. For a cache, that's a mass eviction. For a data store, that's a mass rebalance. Consistent hashing keeps that remapping to roughly 1/N of the keys instead of nearly all of them.

The ring

Hash both the nodes and the keys onto the same circular space (say, 0 to 2^32-1). A key belongs to the first node found walking clockwise from its position on the ring. Add a node: it only takes over the keys between itself and the previous node going counter-clockwise — everything else is untouched. Remove a node: its keys fall to the next node clockwise, again without touching anyone else's keys.

Why virtual nodes

With only one point per physical node on the ring, load gets lumpy — some nodes end up owning a much bigger arc than others just by hash chance, and losing a node dumps its whole slice onto exactly one neighbor. The fix: give each physical node many points on the ring (e.g. hash "node-A-1", "node-A-2", ... "node-A-150"). Now each node's ownership is a scatter of small arcs, load balances out, and a failure spreads its keys across many neighbors instead of one.

Rough sketch

class ConsistentHashRing:
    def __init__(self, nodes, vnodes=150):
        self.ring = {}  # hash -> node
        for node in nodes:
            for i in range(vnodes):
                h = hash(f"{node}-{i}")
                self.ring[h] = node
        self.sorted_hashes = sorted(self.ring)

    def get_node(self, key):
        h = hash(key)
        for ring_hash in self.sorted_hashes:
            if h <= ring_hash:
                return self.ring[ring_hash]
        return self.ring[self.sorted_hashes[0]]  # wrap around

(Real implementations use a sorted structure with binary search instead of a linear scan — this is just the mental model.)

Where I've actually seen this

DynamoDB and Cassandra use it for partitioning. Memcached client libraries use it for picking which cache server a key goes to, specifically so that adding or removing a cache node doesn't blow away the whole cache. Worth digging into how Cassandra also uses it alongside replication (each key replicated to the next N-1 distinct nodes walking the ring) — that part I still need to read more on.

Open question for myself: how do virtual node counts actually get tuned in production — is 150 just a convention, or does it depend on cluster size?
